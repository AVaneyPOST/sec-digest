## General high-severity

- **JetBrains TeamCity On-Premises CVE-2026-63077 — CVSS 9.8, unauthenticated pre-auth RCE via the agent polling protocol.** Reported privately by Antoni Tremblay on 10 Jul 2026 under JetBrains's coordinated-disclosure policy, patched in 2025.11.7 and 2026.1.3, publicly disclosed 27–28 Jul (JetBrains blog + syndicated coverage on 28 Jul). Root cause: insecure deserialization of untrusted data (CWE-502) in the agent-polling protocol. An unauthenticated remote attacker with HTTP(S) reachability to the TeamCity server can bypass authentication checks and execute arbitrary OS commands as the TeamCity service account. Affected: all TeamCity On-Premises versions prior to 2025.11.7 / 2026.1.3. Not affected: TeamCity Cloud (JetBrains reports environments checked, no exploitation attempts observed). Mitigation for anyone who can't upgrade today: JetBrains released a security-patch plugin covering 2017.1 and later, applicable without a full version bump. Historical prior: the last critical TeamCity flaw (CVE-2024-27198, Feb 2024, auth bypass) was mass-scanned and exploited by multiple ransomware crews within days of disclosure; the same clock applies here. Any TeamCity On-Premises reachable from the internet should be patched or taken offline today; internal-only instances still need patching this week because build servers are the classic supply-chain pivot into every downstream artefact. [JetBrains blog (primary)](https://blog.jetbrains.com/teamcity/2026/07/cve-2026-63077/), [Help Net Security](https://www.helpnetsecurity.com/2026/07/28/teamcity-rce-cve-2026-63077-fixed/), [The Hacker News](https://thehackernews.com/2026/07/critical-teamcity-flaw-could-let.html), [TechRepublic](https://www.techrepublic.com/article/news-critical-teamcity-rce-flaw/), [GBHackers](https://gbhackers.com/critical-teamcity-flaw/), [Cybersecurity News](https://cybersecuritynews.com/jetbrains-patch-teamcity-flaw/), [IONIX threat card](https://www.ionix.io/threat-center/cve-2026-63077/). - **BMC / IPMI 2.0 pre-auth password-hash disclosure at scale — Lava research 28 Jul.** Not a new CVE; a fresh internet-scale measurement of CVE-2013-4786, an IPMI 2.0 RAKP-authentication weakness that returns an HMAC-SHA1 hash of the password to any client that initiates a session before authentication. Lava scanned UDP 623 across the public internet as of 6 May 2026 and found 36,872 responsive IPMI services; 24,650 (66%) returned the RAKP message-2 authentication material pre-auth. Cracking-time measurements on modern GPU hardware: HPE iLO factory defaults recoverable in ~1 minute (the factory-default passwords are known-format), Supermicro factory-per-server passwords recoverable in ~1 hour despite the per-server randomisation, because the entropy space is small enough to brute against a HMAC-SHA1 stream given known-plaintext of the challenge. Notified vendors: Supermicro (Jun 2026), accepted the scenario as plausible against current cracking capability and reiterated management-VLAN / ACL guidance. The item to log for any defender: (1) if you have BMCs on any routable prefix, get them off it today, no exceptions; (2) rotate default and legacy factory passwords across the fleet; (3) if exposure ever existed, assume the hash has been captured and cracked — rotate creds and hunt for existing BMC-plane lateral movement; (4) upgrade BMC firmware where vendors have shipped mitigations (Kerberos KDC-side rate limits, disable RAKP entirely in favour of stronger cipher suites where supported). [Help Net Security](https://www.helpnetsecurity.com/2026/07/28/exposed-bmc-ipmi-vulnerability-research/), [BleepingComputer](https://www.bleepingcomputer.com/news/security/over-24-000-exposed-server-bmcs-leak-password-hash-via-decades-old-flaw/), [The Hacker News](https://thehackernews.com/2026/07/24650-internet-exposed-bmcs-disclose.html), [SC Media](https://www.scworld.com/news/ipmi-bug-in-bmcs-found-after-22-years-exposes-24000-plus-servers), [Network World](https://www.networkworld.com/article/4202570/a-13-year-old-flaw-is-exposing-tens-of-thousands-of-data-center-management-systems-2.html), [CSO Online](https://www.csoonline.com/article/4202530/a-13-year-old-flaw-is-exposing-tens-of-thousands-of-data-center-management-systems.html), [Lava primary](https://lavahq.io/research/bmc-exposure-alert), [Tenable plugin 80101](https://www.tenable.com/plugins/nessus/80101). - **Tengu Mirai IoT botnet — hardware-watchdog forensics-destruction technique (Nozomi Networks 27 Jul, syndicated 28 Jul).** Not a new CVE and not a mass campaign, but a notable persistence primitive. Tengu is a Mirai-derived IoT bot targeting Linux CPE/DVR/camera devices; distinguishing feature is that killing its process triggers a forced hardware reboot via the Linux watchdog subsystem, destroying volatile forensic evidence (memory-resident indicators, packet captures held in tmpfs). It also self-monitors its own memory pages via /proc-derived SHA-256 baselines, brick-writes the binary if tampering is detected, and supports 25 DDoS methods, SOCKS5 proxy, shell exec, and system/network telemetry collection. Nozomi's recommended IR sequence: pull the device to an out-of-band capture platform *before* attempting to kill the process, image any non-volatile storage, then apply removal, or you will destroy the evidence you needed. Practical read for any operator with a large CPE / customer-edge fleet: incident-response runbooks that assume kill → rotate credentials → return to service will lose forensic ground on these hosts.
