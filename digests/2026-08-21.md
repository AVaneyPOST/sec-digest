## TL;DR

- **Zimbra CVE-2026-73570 — CVSS 8.9 unauth RCE in SNMP notification processing — active exploitation confirmed 2026-08-20.** Patched in 10.1.20 on 2026-07-20 (one-month gap between fix and exploitation reporting). Attack requires the optional `zimbra-snmp` package installed + `snmp_notify` enabled + swatchdog running — a common webmail-monitoring config, not a niche one. Command injection into OS commands with Zimbra-user privileges via specially-crafted SMTP requests. CERT Polska + Belgium CCB both flagged the urgency in-window. Shadowserver tracks ~12,100 exposed Zimbra servers online, concentrated in Europe (4,382) and Asia (4,492). **CRITICAL** for anyone still running unpatched Zimbra — patch or take SNMP notifications offline.
- **isolated-vm — critical type-confusion sandbox escape (GHSA-864f-rcv7-6rh4) disclosed 2026-08-20 by Endor Labs.** Affects all versions ≤ 7.0.0; patched in 6.2.0 and 7.0.1 earlier this month. `ExternalCopy.transferList` type confusion corrupts memory in the host Node.js process — guest-to-host escape demonstrated end-to-end (controlled-address crash → hijacked host control flow). No CVE yet assigned. Library sees > 1M weekly downloads and is the sandbox layer inside **n8n**, **Sim.ai**, **Mastra**, and **Activepieces** — the popular Node.js AI-agent stacks. Any deployment running untrusted JS through those frameworks should treat this as an immediate RCE on the host. **HIGH**.
- **CISA KEV — CVE-2026-64849 (MLflow SSRF, CVSS 9.6) was added 2026-08-19 (Wednesday), missed in yesterday's digest.** Yesterday's "no KEV additions in-window" was wrong: MLflow's SSRF was the one addition, added the same day as the Cisco Wednesday batch, with active exploitation for cloud-metadata-service credential theft observed hours after CVE assignment on 08-17. All MLflow < 3.15.0 affected, unauth remote. Scanning campaigns pivoted to IMDS credential exfil → cloud-resource enumeration → cryptominer / IAM-persistence. Any exposed MLflow instance on any cloud tenant is the primary risk profile. **HIGH → CRITICAL**. See correction note below.
- **Telecom operator side quiet.** No fresh confirmed telco-carrier breach disclosure, GSMA / FASG communication, or telecom-vendor PSIRT advisory in-window. Manic (below) is the closest telecom-adjacent item — mobile threat, not signalling threat.
- **No new CISA KEV additions dated 2026-08-20.** Wed 08-19's KEV addition (MLflow, above) is the last one; Mon 08-18's four (IKEv2 / SharePoint / vCenter / macOS Screen Sharing) all still have running BOD 26-04 clocks.

## Telecom

**Manic — Android banking trojan + spyware with Wi-Fi Direct / Bluetooth mesh-relay exfiltration** — [BleepingComputer — Manic Android malware exfiltrates via nearby devices](https://www.bleepingcomputer.com/news/security/new-manic-android-malware-can-exfiltrate-data-through-nearby-devices/), [ThreatFabric — Manic blog](https://www.threatfabric.com/blogs/manic-blend-between-banking-malware-and-spyware), [The Hacker News — Manic offline-device exfiltration](https://thehackernews.com/2026/08/manic-android-malware-exfiltrates-data.html), [Cybersecurity News — Manic banking PINs](https://cybersecuritynews.com/manic-android-malware/) — ThreatFabric analysis published 2026-08-20 — **HIGH (mobile) / NOTABLE (telecom)**
Not a signalling threat, but the closest telecom-adjacent item in-window. Manic sits at the intersection of Android banking trojan and mobile spyware — targets 169 apps spanning banking, government / eID portals, payment, crypto wallets & exchanges, authenticator / 2FA, and messaging. **Ukraine is the primary target set** (national banks + eID); target list extends to RU, PL, DE, CZ, SK, UK. Novel capability worth calling out for any operator whose fraud / risk team monitors handset-side compromise: **Wi-Fi Direct + Bluetooth mesh relay** for data exfiltration through nearby infected devices when direct C2 is unavailable — a fallback path that survives operator-level filtering / airplane-mode isolation of the primary infected handset. Overlays on numeric keypads capture PINs while letting the legitimate app continue functioning through Android Accessibility replay. Infrastructure traces to February 2026; July 2026 refresh added stronger anti-analysis and in-memory core-loading (harder for MDM / MTD tooling to fingerprint). Telecom relevance: this is what mobile-first fraud & abuse teams should be modelling right now for the 2FA / SMS-OTP / RCS-side attack surface, and any operator MDM push to enterprise fleets in the affected countries should add Manic IOCs to the loaded ruleset.

## General high-severity

**Zimbra CVE-2026-73570 — SNMP notification command injection, unauth RCE, active ITW exploitation** — [BleepingComputer — Critical Zimbra RCE now actively exploited](https://www.bleepingcomputer.com/news/security/critical-zimbra-rce-flaw-now-actively-exploited-in-attacks/), [Belgium CCB advisory](https://ccb.belgium.be/advisories/warning-actively-exploited-remote-code-execution-zimbra-collaboration-patch-immediately), [The Hacker News — Zimbra SNMP RCE](https://thehackernews.com/2026/08/attackers-exploit-zimbra-snmp-flaw-for.html), [NVD — CVE-2026-73570](https://nvd.nist.gov/vuln/detail/CVE-2026-73570), [The Hacker Wire — Zimbra SNMP notifications RCE](https://www.thehackerwire.com/zimbra-collaboration-rce-in-snmp-notifications-cve-2026-73570/) — patch 2026-07-20, active exploitation confirmed 2026-08-20 — **CRITICAL**
CVSS 8.9. Improper sanitization of untrusted input in the SNMP notification processing path — an attacker can send specially-crafted SMTP requests to inject data into OS commands, gaining arbitrary command execution with Zimbra user privileges. Attack requires all three of: `zimbra-snmp` optional package installed, `snmp_notify` parameter enabled, `swatchdog` service running. That combination is not niche — it's the standard SNMP-monitoring config anyone running Zimbra with an SNMP-based monitoring stack (Nagios / Zabbix / Prometheus-SNMP-exporter) would have. **Patched 2026-07-20 in Zimbra Collaboration 10.1.20** — the one-month patch-to-exploitation gap is short by unpatched-webmail-server standards; CERT Polska + Belgium CCB both put out actively-exploited advisories in-window. Shadowserver telemetry: **12,100+ Zimbra servers exposed online** (Europe 4,382 / Asia 4,492 dominate the count). If you have unpatched Zimbra in scope, this jumps the queue over every other pending patch this week. Post-exploitation is straightforward — webshell-drop into the Zimbra web root, or persistence via Zimbra cron.

**isolated-vm GHSA-864f-rcv7-6rh4 — type-confusion sandbox escape, guest JS → host Node.js RCE** — [Endor Labs — GHSA-864f-rcv7-6rh4 isolated-vm](https://www.endorlabs.com/learn/ghsa-864f-rcv7-6rh4-critical-type-confusion-vulnerability-in-isolated-vm), [The Hacker News — isolated-vm sandbox escape](https://thehackernews.com/2026/08/isolated-vm-flaw-lets-sandboxed.html), [DevOps.com — isolated-vm sandbox escape RCE](https://devops.com/critical-flaw-in-isolated-vm-can-lead-to-sandbox-escape-rce-threat/), [CSO Online — critical flaw patched in popular JS sandbox](https://www.csoonline.com/article/4212151/critical-flaw-patched-in-popular-javascript-sandbox-used-in-ai-projects.html) — disclosed 2026-08-20 by Endor Labs, patched 2026-08-XX earlier this month — **HIGH**
isolated-vm is the Node.js wrapper around V8 Isolates that most Node-based sandboxes settle on for "run untrusted JS in-process, get real isolation." No assigned CVE yet — track as **GHSA-864f-rcv7-6rh4**. Affects all versions ≤ 7.0.0. Patched in **6.2.0** (LTS branch) and **7.0.1** (main), both released earlier this month. Root cause: type confusion in `ExternalCopy`'s handling of the `transferList` option — guest code can corrupt memory in the host Node.js process, escalated end-to-end from controlled-address crash to hijacked host control flow (a full sandbox escape). Downstream impact set: **n8n, Sim.ai, Mastra, Activepieces** — the popular Node.js AI-agent orchestration frameworks that all use isolated-vm as the "run this untrusted model-generated tool code" boundary. Any deployment allowing model / LLM output or user code through those frameworks should treat this as a "the sandbox is a lie until you patch" scenario — the LLM-tool-code → server RCE path is now confirmed, not theoretical. > 1M weekly npm downloads underlines how many dependencies inherit this. Fix priority: upgrade to 6.2.0 (if pinned to 6.x for API compatibility) or 7.0.1.

**MLflow CVE-2026-64849 — CVSS 9.6 unauth SSRF → cloud-credential theft — added to CISA KEV 2026-08-19 (correction: missed in yesterday's digest)** — [CISA alert — MLflow KEV addition](https://www.cisa.gov/news-events/alerts/2026/08/19/cisa-adds-one-known-exploited-vulnerability-catalog), [Security Affairs — MLflow KEV addition](https://securityaffairs.com/197558/hacking/u-s-cisa-adds-a-mlflow-flaw-to-its-known-exploited-vulnerabilities-catalog.html), [SecurityWeek — MLflow exploited for cloud credential theft](https://www.securityweek.com/mlflow-vulnerability-exploited-for-cloud-credential-theft/), [BleepingComputer — CISA warns MLflow exploited](https://www.bleepingcomputer.com/news/security/cisa-warns-of-hackers-exploiting-critical-mlflow-vulnerability/), [Rapid7 CVE-2026-64849](https://www.rapid7.com/db/vulnerabilities/cve-2026-64849/) — CVE assigned 2026-08-17, exploitation observed same-day, KEV addition 2026-08-19 — **CRITICAL**
Critical-severity SSRF in MLflow (open-source ML-workflow platform). All versions **< 3.15.0** affected. Unauthenticated. Attackers exploit the SSRF to send HTTP requests to internal endpoints — the primary payoff is cloud metadata service (`169.254.169.254` on AWS / GCP / Azure IMDS) → exfiltrate temporary cloud credentials → enumerate cloud resources → deploy cryptominers OR establish IAM-user / IAM-role persistence for follow-on. Widespread opportunistic scanning was observed within hours of CVE assignment (08-17). CISA gave federal agencies two weeks to patch; KEV addition was **2026-08-19** — same day as the Cisco Wednesday batch. Yesterday's digest incorrectly reported KEV as empty in-window; the MLflow addition was the sole entry that day. Practical scope for a red-teamer: MLflow exposed on any cloud tenant (default deployment pattern is behind ML-ops team's private VPC, but any misrouted ingress rule or a "just this one for dev" internet exposure is game over for that tenant's IAM). Any org running MLflow tracking servers should audit for < 3.15.0 exposure regardless of federal-agency status.
