## General high-severity

- **Steam forum ClickFix → PowerShell → XMRig cryptominer campaign, first-party gaming-platform social layer as the delivery surface.** BleepingComputer's 26 Jul write-up. Operators create throwaway Steam accounts and monitor discussion threads for real problem reports — game crashes, missing inventory items, install failures — then reply with a "fix" that instructs the victim to open PowerShell as Administrator and paste a supplied command. The command silently downloads and executes XMRig, masquerades as a "Windows optimisation utility," adds a Microsoft Defender exclusion for its working directory, hides its files under `C:\Windows\Background\`, and creates a scheduled task with names beginning `XMRig-` that runs the miner with SYSTEM privileges at every startup. What makes the campaign worth logging: (a) delivery through a first-party gaming platform's own social feature bypasses the enterprise defensive plumbing that assumes attacker infrastructure is external, and (b) the "helpful stranger tells you to run PowerShell as admin to fix your problem" playbook generalises trivially to Discord, Reddit, GitHub Issues, StackOverflow, and any other high-trust support venue. Practical hunt: `C:\Windows\Background\` directory presence, `XMRig-*` scheduled tasks, Microsoft Defender exclusions whose creation is not present in your change-management record. Awareness: any support workflow that ends "run this PowerShell command as Administrator" should be treated as suspicious by policy. [BleepingComputer](https://www.bleepingcomputer.com/news/security/steam-forum-clickfix-attacks-infect-gamers-with-xmrig-cryptominers/), [Windows Report](https://windowsreport.com/hackers-use-steam-forums-to-push-xmrig-miner/), [TechEchelon](https://www.techechelon.com/post/steam-forums-weaponized-in-clickfix-campaign-distributing-xmrig-cryptominers). Date: 2026-07-26. [NOTABLE]

- **Hotel/conference Wi-Fi DNS-poisoning + Microsoft device-code-flow abuse → Microsoft 365 account takeover, MFA not defeated but weaponised.** ReliaQuest's Threat Spotlight was published 23 Jul; BleepingComputer picked it up on 25 Jul and Security Affairs on 26 Jul, and coverage continued to broaden through today's window. The chain: attacker compromises a hospitality Wi-Fi gateway (weak/reused admin creds, exposed management interfaces), gains administrative access, and rewrites DNS settings so every associated client is redirected to attacker infrastructure. On some paths the redirect delivers a fake M365 sign-in page and harvests credentials the classical way. The more interesting path abuses **Microsoft's own OAuth 2.0 device-authorisation grant flow**: the attacker initiates a device-code request against Entra ID from their own infrastructure, obtains a user-code, injects a prompt at the redirect layer that tells the victim "sign in to complete network access — enter code XXXX at microsoft.com/devicelogin", and the victim, on their real corporate device, authenticates through their real MFA to their real Microsoft tenant and pastes the attacker-supplied code. Microsoft's servers issue valid access + refresh tokens to the attacker's device. MFA works exactly as designed and the attacker walks away with legitimate token material. Active against organisations with devices connecting through affected gateways in multiple US cities plus India and Saudi Arabia; verticals include financial services, legal, healthcare, energy, retail, and professional services. Tradecraft overlaps techniques previously associated with APT28, but researchers stopped short of attribution. Practical actions: enforce Conditional Access to block or restrict the device-code flow (either disallow it, or gate to compliant device + trusted origin only); require Continuous Access Evaluation and short refresh token lifetimes; treat corporate-device use on shared/unmanaged Wi-Fi as a lower-trust context by default. [BleepingComputer](https://www.bleepingcomputer.com/news/security/hackers-hijack-hotel-wi-fi-dns-to-steal-microsoft-365-accounts/), [Security Affairs](https://securityaffairs.com/196017/security/hackers-hijack-hotel-wi-fi-to-steal-microsoft-365-credentials.html), [Infosecurity Magazine](https://www.infosecurity-magazine.com/news/hotel-wifi-dns-poisoning/), [ReliaQuest original](https://reliaquest.com/blog/threat-spotlight-dns-poisoning-tactics-expand-to-hospitality/), [CyberInsider](https://cyberinsider.com/hackers-use-dns-poisoning-on-hotel-wi-fi-to-steal-microsoft-365-accounts/). ## Worth watching

- **Chaos ransomware / msaRAT — Rust-based RAT that routes its entire C2 through the victim's own Chrome/Edge via CDP + WebRTC/TURN, so the network only sees a browser talking to Cloudflare and Twilio.** Cisco Talos disclosure 23 Jul, press wave running into 26 Jul (Security Affairs, BleepingComputer, The Hacker News, Latest Hacking News). The RAT launches Chrome/Edge in headless mode with remote debugging enabled, drives the browser over Chrome DevTools Protocol, and pushes every command / exfil packet through a WebRTC DataChannel relayed by Twilio's TURN infrastructure to a Cloudflare Workers endpoint. The malware process itself never opens a network socket. Deployed after initial access and before the Chaos encryptor stage, consistent with Chaos's usual pre-encryption recon rhythm. Detection surface has to move to the endpoint: Chrome/Edge launches with `--remote-debugging-port` from non-developer parent processes, headless-browser instances the user did not start, CDP session initiation from local ports the browser is not normally listening on, WebRTC data-channel volume from browser processes that never made a corresponding user-facing navigation. Traditional egress inspection sees legitimate CDN traffic and passes it. [Cisco Talos original](https://blog.talosintelligence.com/chaos-msarat-living-off-the-browser-to-build-covert-c2-channel/), [Help Net Security](https://www.helpnetsecurity.com/2026/07/23/cisco-talos-chaos-ransomware-msarat/), [BleepingComputer](https://www.bleepingcomputer.com/news/security/new-msarat-malware-uses-chrome-edge-browsers-to-route-c2-traffic/), [The Hacker News](https://thehackernews.com/2026/07/chaos-ransomware-uses-msarat-to-route.html), [Latest Hacking News (26 Jul)](https://latesthackingnews.com/2026/07/26/msarat-chaos-ransomware-browser-c2/).
