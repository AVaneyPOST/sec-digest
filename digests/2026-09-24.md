## Telecom

- **F5 BIG-IP APM — CVE-2026-94127 (CVSS 9.8 v3.1 / 9.3 v4.0), scope clarification 2026-09-23 00:45 UTC.** F5 updated the CVE record to say the heap-based buffer overflow in TMM's OAuth handling is present **only in the OAuth Authorization Server role** of APM — i.e. VSes with an APM access policy plus an OAuth profile where APM is issuing tokens, not merely consuming them. Client-side/resource-server APM configurations are excluded. The advisory was originally read as "any APM+OAuth VS", so operators should re-run their inventory before rolling hotfixes — the addressable surface is smaller than we said yesterday, but the exploited path (unauth, data-plane, root as TMM) is the same. Telco relevance unchanged: subscriber-portal SSO, N32 SEPP fronts, IMS HTTP proxies and B2B API gateways that federate to a carrier's IdP are exactly the deployments most likely to run APM as an OAuth AS. [BleepingComputer](https://www.bleepingcomputer.com/news/security/f5-warns-of-big-ip-apm-remote-code-execution-zero-day-exploited-in-attacks/) · [The Hacker News](https://thehackernews.com/2026/09/f5-patches-critical-big-ip-apm-zero-day.html) · [SecurityWeek](https://www.securityweek.com/critical-f5-big-ip-vulnerability-exploited-as-zero-day/) · [Field Effect](https://fieldeffect.com/blog/f5-fixes-big-ip-apm-vulnerability) — 2026-09-23 (record update) — CRITICAL

- **Lantronix SLC8000 / EMG-series — CVE-2026-80155 (CVSS 10.0), published 2026-09-22, first cross-corroborated 2026-09-23.** Authentication-bypass path traversal in the web management portal's file-upload endpoint. The session-cookie file path is built with a fixed-size `snprintf`; a specially sized cookie causes the path to truncate at the delimiter, and path traversal from there lets the auth check consult an attacker-supplied on-disk file (e.g. the local user DB) — bypassing the session gate and yielding unauth arbitrary file read plus arbitrary write, i.e. RCE on the console server. Fixed in SLC8000 v9.7.0.5 and EMG8500/EMG7500 v9.7.0.1; **SLB882 and SLCx-03/-02 remain vulnerable on every firmware version** with no patch. Companions in the same family: CVE-2026-80156 (SLC8000 path traversal, 9.1) and CVE-2026-80152 (SLC8000 OS command injection, 9.1). Telecom relevance is direct: SLC/EMG boxes sit in NOCs, MSC/BSC rooms and colo cages as **out-of-band serial console access** to routers, SBCs, base station controllers, firewalls and signalling nodes — compromise gives an attacker the same physical-console power a field tech has, over every device on the strip, past whatever in-band controls the network uses. [OffSeq threat page](https://radar.offseq.com/threat/cve-2026-80155-improper-limitation-of-a-pathname-to-a-restricted-directory-path-traversal-in-lantronix-7f7b828320010fd9) · [Strix analysis](https://www.strix.ai/cve/CVE-2026-80155) · [ThreatInt CVE record](https://cve.threatint.com/CVE/CVE-2026-80155) — 2026-09-22 disclosure — CRITICAL

- **InfraTrust September Pulse — network **management** systems are the top exploited class for a second consecutive month, 2026-09-23.** Between 2026-08-25 and 2026-09-17: 158 advisories, 1,699 CVEs across 17 vendors, 42 critical, 5 promoted to KEV. The report names the three items driving the pattern — **Cisco Secure Firewall Management Center CVE-2026-20079** (CVSS 10, auth bypass → root command exec via crafted HTTP to the FMC web UI, in KEV), **Cisco Identity Services Engine CVE-2026-76460** (auth bypass in an API → root command exec, in KEV) and **Linux kernel CVE-2026-31431 "CopyFail"** (local priv-esc, in KEV since May, now referenced in 19 downstream vendor advisories from six vendors). Framing for telco: policy engines (ISE), firewall managers (FMC) and Linux-based EMS/OSS underlays are the natural entry points because control of one manager gives you fleet-wide reconfig, cert issuance and log tampering — far higher ROI than compromising an individual edge. ## Worth watching

- **"ConfigConfusion" — one Kubernetes YAML → GCP org takeover via KCC, 2026-09-23.** Justin O'Leary detailed a confused-deputy chain in Google Config Connector: any Kubernetes user with `create` on `IAMPolicyMember` in a namespace watched by KCC can grant themselves `roles/owner` at the GCP organization level, because KCC executes every GCP API call as its own service account (typically over-privileged) rather than as the requesting user. Google's position is working-as-designed — this is a per-deployment hardening problem: scope KCC's SA per namespace, strip broad roles, or use Config Connector Kustomize's `iam.cnrm.cloud.google.com` guardrails. Telco / MSSP relevance: multi-tenant GKE clusters that host signalling / OSS / analytics workloads across customer namespaces are the exact deployment shape this exploits. [BleepingComputer](https://www.bleepingcomputer.com/news/security/how-one-kubernetes-yaml-can-hand-over-a-gcp-organization/) · [SOCRadar analysis of GKE priv-esc chains](https://socradar.io/blog/misconfigurations-in-google-kubernetes-engine-gke-lead-to-a-privilege-escalation-exploit-chain/) — 2026-09-23 — HIGH (misconfiguration, not CVE)

End state: PII/PCI exfil + skimmer implants on checkout pages. ~488k of the ~600k cards are US-issued. Cost ~$25 per targeted company. Not a telco story on its face, but it's the first documented mass-scale campaign where the actual exploitation loop is agentic — implications for carrier B2C portals and any hosted checkout/BSS surface.
